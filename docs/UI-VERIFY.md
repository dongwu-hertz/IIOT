## 一、怎么拿到这批截图

截的不是空壳：脚本会把你**真实**的数据库**复制**一份到一次性 profile，所以截图里是你的真设备
（2026-09-17 收盘时库里是 **3 台**：AE08、Acoustic Camera、SN-16 空气声呐）。

```powershell
# 先构建（改了源码之后必须）
node .\node_modules\electron-vite\bin\electron-vite.js build

# 出图：--with-data 复制真实库；截图落在 .demo-shots-real\
node scripts\demo-shot.cjs --with-data --out .demo-shots-real
```

三件必须说清楚的事：

1. **只读复制，不动原库。** 你的应用可能正在运行，脚本只 `copyFileSync` 出去（WAL 模式下连同
   `-wal` / `-shm` 一起复制，否则会拿到缺最近提交的旧快照）。
2. **副本里的账号被清空了。** 真实库里的管理员密码是你自己改过的，探针不知道也不该知道；
   而 `AuthService.ensureSeedAccount()` 每次启动都会在"用户表为空"时重建出厂管理员
   （`admin` / `Hz@123456`，首次登录强制改密）。清的是**副本**，设备和通道都留着。
3. **原库一个字节都没写。** 想确认可以比对文件时间戳。

截图是静态的，交互（点告警图标、点添加设备、拖窗口改尺寸）得自己点。两种方式：

```powershell
# 开发模式（改代码即时生效）
npm run dev

# 或者用刚构建的产物
npm run start
```

⚠️ 这两种都会用**你真实的 profile**（`%APPDATA%\hertzinno-acoustic-box-manager`）。
如果你现在正开着应用，先关掉那一个再启动，否则两个实例会抢同一个数据库。
（探针那条 `--with-data` 路径不受影响：它走一次性 profile。）

## 六、第 7 批：四条**没验证**的（不要按已验证验收）

1. **声呐（SN-16 / 听诊盒子）的实时流一条都没接**。手册给的是三条 WebSocket 路径
   （`/audio_stream`、`/stft_stream`，SN-16 另有 `/all_chns_stream`），我们既没有接入，
   也没有在真机上验过帧格式。所以「查看」进到声呐那一屏时，看到的是**参数 + 告警同步 +
   本机录音回放 + 安装点位**，没有实时图 —— 界面上那句"实时流尚未接入"就是这件事的说明。
   要实时图的话请给一句：这一族你要看的是**声源方位（`horizontal`/`vertical`）变化的实时图**，
   还是**这一路的实时音频/时频图**？两者的协议工作量与可验证程度不一样。
2. **双击 IP 弹出的那个浏览器页面本身没看过**：探针把 `shell.openExternal` 换成了替身
   （自动化验证不该真的弹浏览器），所以"链路通、URL 对"是证明过的，**浏览器里那一页长什么样**
   没看过 —— 你双击一次就知道了（设备自己的 Web 界面，我们控制不了它）。
3. **真机上的"界面上录入点位"**：真机验证用的是 CLI 驱动（同一个 IPC 链路，`devices.add`
   带安装信息并读回），**不是在窗口里手点那四个框**。窗口那一遍是在假设备上跑的。
   两者的差别只是"输入框→表单状态"这一段，但这一段确实是真机没走过的。
4. **设备变多时的表格表现**：现场只有 2–3 台设备，表头吸顶、行高、横向滚动在 30 台左右
   的情况下都没量过。

> 还有一条**操作层面的注意**（不是缺陷，但要你知道）：机型自动识别是**按顺序探活**
> （声纹 → 听诊盒子族 → 相机）。对一台听诊盒子/声呐来说，第一步的声纹探活会发几次
> **注定失败**的登录（实测假设备上 8 次 `POST /login`）。如果某台设备对失败登录有锁定策略，
> 这里可能触发它 —— 这一条**没有验证过**（真机上只跑过一次，没看到异常）。
> 若你在设备日志里看到这些失败登录并介意，可以改为"先问一次 `/system`，谁答得像就走谁"，
> 但那需要设备在未认证时也回 `/system`（目前未确认）。

## 七、第 8 批：五条**没验证**的（不要按已验证验收）

1. **真机上的 PTZ 写入 —— 这一次根本没跑成**。你同意的那一次"把当前值原样写回再读回"
   写进了 `scripts/e2-live-proof-driver.cjs`，但 2026-09-17 21:4x 与 22:0x 两次检查，
   那台 SN-16（**192.168.110.234**）**都不在线**：三种协议全部超时，
   `ping` 与 `http://192.168.110.234/` 也都不通（同一天下午它还以 108 ms 应答过）。
   所以"PTZ 写到真设备上通不通"**至今没有证据**。
   **不过这条链本身已经先跑通了**：我加了一个进程外的假 SN-16
   （`scripts/mock-air-sonar.cjs`），把同一套 `e2-live-proof` 指向它 →
   **0 problems**，其中就包括新加的「读 PTZ → 原值写回 → 读回逐项比对」（`allApplied: true`）
   与「抓图 3 张落库并按告警取回」。所以现在缺的**只剩"那台设备自己怎么回"**。
   **设备一上线跑这一条就行**：
   ```
   node scripts/e2-live-proof.cjs --ip 192.168.110.234 --password 123456
   ```
   （它会先读 PTZ → 原值写回 → 再读回来逐项比对，**不会**改动球机的实际配置。）
2. **「与球机对时」按钮的效果**：手册只列了端点、没写请求体，我们发一个空对象；
   真机上没点过，它到底做了什么**未验证**。
3. **真机上的抓图一张都没见过**：这台设备上 1001 条告警里只有 6 条 `files_status=1`，
   而这 6 条的 `1.jpg` 也全是 404（设备自己的网页播放器同样取不到）。
   所以"点声呐看截图"在真机上**一次都没有成功过** —— 有图那条链是在假设备上验的。
4. **抓图的张数与内容**：手册说最多 3 张、1 秒一张；少于 3 张属于正常（重启后可能只剩一部分），
   但真机上没见过任何一张，所以**图的尺寸、清晰度、是不是球机画面**都不知道。
5. **你自己在窗口里点一遍**：上面那一整套（PTZ 页签 → 保存 → 读回核对 → 点位图 → 抓图）
   是在**假设备**上由探针点的。窗口里手点一遍才能真正确认手感与文案，
   尤其是「安装点位」录进去之后**图上的相对位置对不对** —— 那要靠你拿现场点位核对
   （软件不做任何坐标校验，只校验范围）。

> 另外**一件要告诉你的现场状态**：你真实的库里现在有 3 台设备
> （AE08 `192.168.110.90`、Acoustic Camera `192.168.110.235`、SN-16 `192.168.110.234`），
> 库版本还是 **v11**；装上新包第一次打开时它会自动升到 **v12**（加两列，
> `devices.e2_variant` 与 `alarms.snapshot_dir`，迁移有单测覆盖、不删任何数据）。
> 那台 SN-16 现在显示离线是**设备不在线**（同一时刻 ping 不通），不是软件把它标错了。

## 八、真机那一条：设备上线之后你自己怎么跑（一分钟的事）

```
node scripts/e2-live-proof.cjs --ip 192.168.110.234 --password 123456
```

它跑的是**真应用的主进程**（真设备服务、真存储、真回环端点），**不碰你的库与设置**
（一次性 profile；存储根也会被挪到那个临时目录里）。预期看到（最后一行是最要紧的）：

```
[e2] probe      : {... "kind":"auscultationBox" ... }
[e2] install    : {"typed":{...},"readBack":{...}}        ← 两者必须一样
[e2] status     : {"ok":true}   variant: airSonar
[e2] sync       : {"ok":true}   outcome: {...}
[e2] snapshots  : {"ok":true,"states":["ok"],"files":N}   ← N 可能是 0（设备上没图，见 §七.3）
[e2] ptz before : {... 球机那一组当前值 ...}
[e2] ptz write  : {"ok":true}   applied: true             ← 原值写回成功且读回一致
[e2] problems   : 0
```

- **`ptz write applied: true` = 那台设备接受整份 `PUT /system` 且读回一致** —— 这就是
  PTZ 那条链在真机上的证据。写进去的是**设备当时给的原值**（`cam_ip`/`cam_port`/账号/口令
  一个都没改），所以**不会动现场联动的球机**。
- 出现 `ptz write` 失败（404/400/超时）时把那一行发我 —— 那说明这一版固件的写入口
  与手册不一样（就像 READ 路径那样，V3.4.0 的 `/get_*` 全是 404），我按实际回话改。
- `problems` 不是 0 时，每一行都会写清是哪一步、期望什么、实际什么。
- 没有真机的时候想先看这条链跑起来的样子：
  `node scripts/mock-air-sonar.cjs --port 9301 --password admin123`（另开一个窗口）
  然后 `node scripts/e2-live-proof.cjs --ip 127.0.0.1 --port 9301 --password admin123 --spectrograms`
  —— 这一条我已经跑过，**0 problems**（含抓图 3 张与 PTZ 原值写回）。
