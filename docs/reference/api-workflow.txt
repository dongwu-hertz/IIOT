Overview
Document Purpose
This document describes the complete workflow for calling the open interfaces of the onboard acoustic camera: login authentication → parameter configuration → start detection → subscribe to real-time data (WebSocket) → obtain detection results → end detection. It also provides an interface list and call examples.
Document Description
This document is compiled from Chapter 5, “Open Interface Description,” of the Onboard Acoustic Camera / Mini Acoustic Camera User Manual v1.0 (Partial Discharge Detection Version), and can serve as the interface-integration baseline for secondary development and system integration.
Interface Overview
HTTP interfaces (REST): used for authentication, parameter configuration, starting/stopping detection, log/file retrieval, alarm-strategy management, etc.
WebSocket interfaces: used to obtain FFT, acoustic signature, PRPD, abnormal-noise localization points, PCM audio, and detection results in real time.
RTSP interface: used to obtain the video stream.
Key Terms
token: authentication token issued after login. All subsequent HTTP requests must include it in the Authorization header; failed or invalid authentication returns 401.
Acoustic-field configuration: upper/lower analysis frequency-band limits (freq_up_limit / freq_down_limit, unit: kHz).
Imaging configuration: imaging threshold energy_threshold, number of detection targets target_number, imaging sensitivity imaging_sensitivity, and imaging enhancement imaging_enhance.
Detection mode: `run_mode`: 1 = single detection; -1 = smart patrol.
RTSP: video streaming protocol. The default video_port in the video parameters is 443.
Quick Start
The complete API workflow for switching modes is shown below. (Note: The device supports only one operating mode when shipped. If mode switching is required, please contact technical support.)

Login Authentication (POST /login)
Enable alarm strategy ID=1 (PUT /alarm_strategy)
Adjust device imaging parameters; set the imaging frequency band to 20 kHz–40 kHz (PUT /system/acoustic)
Start detection (POST /turn_on_detect); returns the alarm-record ID.
Obtain detection result: GET detect_logs/{detect_id}; obtain result file: GET detect_file/{log.saving_path}/{logs.file_name}
Disable alarm strategy ID=1 (PUT /alarm_strategy)
End.

C. Enable/Disable Alarm Strategy

In actual production environments, an alarm strategy is usually enabled according to the workflow above. First call the query interface (GET /alarm_strategy_enable) to check whether an alarm strategy is already enabled; then call the update interface (PUT /alarm_strategy_enable) to enable or disable the required strategy.
Scenario 1: Assume the query interface (GET /alarm_strategy_enable) shows that the system contains three alarm strategies: A (switch=0), B (switch=0), and C (switch=0), meaning all three are disabled. If the business requirement is to enable strategy A, simply call the update interface (PUT /alarm_strategy_enable) to enable strategy A.
Scenario 2: Assume the query interface (GET /alarm_strategy_enable) shows that the system contains three alarm strategies: A (switch=1), B (switch=0), and C (switch=0), meaning strategy A is enabled and the others are disabled. If the business requirement is to enable strategy B, first call the update interface (PUT /alarm_strategy_enable) to disable strategy A, then call it again to enable strategy B.
Note: Due to system-resource limitations, the device can have at most one alarm strategy enabled at any given time.

Start Detection
Interface
Method
Description

/turn_on_detect
POST
Used to issue the start-detection command.
Single mode: detection ends after one cycle; the result can be viewed on the Data page.
Smart-patrol mode: repeatedly executes the enabled alarm strategy; a record is saved and generated only when an alarm is triggered.

/turn_off_detect
POST
Used to issue the stop-detection command.
Single mode: immediately ends the current detection. Current record duration = end time - start time. In particular:
This interface can be used to stop detection before the alarm-strategy period ends. If the alarm period is exceeded, the system stops detection automatically and the stop interface does not need to be called again.
Detection-record duration is measured in seconds. If the alarm-strategy period is 1 s and the stop-detection interface is called within 1 second, the detection-record duration is 1 second. If the detection period is 13 seconds and the stop-detection interface is called after 2.6 seconds, the detection-record duration is 3 seconds.
Smart-patrol mode: immediately ends the repeated detection cycle.

/system/detect_status
GET
Used to obtain the current detection status and determine whether the device is currently detecting.

A. Single Detection:

The above shows the complete single-detection process. Call the start-detection interface (POST /turn_on_detect).
The device starts acquiring data. Based on the “enabled alarm-strategy period” (the length of a strategy cycle, adjustable from 1 to 30 seconds according to actual requirements), the device acquires spatial acoustic-signature and visible-light data for one cycle, calculates feature values, and determines whether the results trigger an alarm. When the start-detection interface (POST /turn_on_detect) succeeds, it generates a record ID. The generated detection-log details can be obtained using that record ID. A record is generated regardless of whether an alarm is triggered. Single-detection mode is recommended during the early exploration and validation stage of a project.
B. Smart Patrol:

The above shows the complete smart-patrol process. After the start-detection interface (POST turn_on_detect) is called and smart patrol is enabled, the device performs periodic acquisition and analysis according to the enabled alarm strategy. If an analysis result triggers an alarm, the corresponding record is saved; otherwise, the analysis result is discarded. Smart-patrol mode is recommended when the business application is mature and stable and the existing alarm strategy can meet the requirements. At any time during the process, the current detection status can be queried using GET /system/detect_status.

Note:
Before calling the start-detection interface, make sure that one alarm strategy is enabled.
Single-detection mode: each call to the start-detection interface (POST turn_on_detect) generates one record.
Smart-patrol mode: after calling the start-detection interface (POST turn_on_detect) and enabling smart patrol, the device performs periodic acquisition and detection according to the enabled alarm strategy. A record is saved only when an alarm is triggered.

Alarm Push
-
Used to push detection data to a specified service.

There are three methods for obtaining detection results
Method 1: WebSocket Protocol
WebSocket request address: ws://localhost:port/detectFeedback. After each detection, the device returns one packet of detection-result data as a JSON string. Parse the returned data according to byte order, then construct http://{IP}:{port}/detect_file/{log.saving_path}/{logs.file_name} to obtain the corresponding result file.

Method 2: Obtain the Detection Result Record by ID

The above shows how to obtain the corresponding detection record by ID. In single-detection mode, the start-detection interface (POST turn_on_detect) returns a record ID. Wait until the detection is complete (GET /system/detect_status can be used to check whether detection has ended), then wait 1–10 seconds and call GET detect_logs/{detect_id} to obtain the result. Based on the returned record, construct http://{IP}:{port}/detect_file/{log.saving_path}/{logs.file_name} to obtain the corresponding result file.

Note: If GET detect_logs/{detect_id} is called immediately after detection ends, no record may be returned because data acquisition has just completed and analysis and saving require processing resources and time. With a typical 1-second alarm-strategy period, analysis and saving take several hundred milliseconds. This time increases as the alarm-strategy period becomes longer. Determine an appropriate wait time through testing for the actual application.

Method 3: Alarm Push

The device can automatically push alarm records to a specified server. In the example above, the custom service endpoint is http://192.168.2.50:8080/logs. When the device generates an alarm record, it immediately pushes the record as JSON over HTTP to the specified service on host 192.168.2.50. Construct http://{IP}:{port}/detect_file/{log.saving_path}/{logs.file_name} to obtain the corresponding result file.

Exception Handling
401 authentication failure: the token is missing or invalid. Call POST /login again to obtain a new token and retry.
WebSocket disconnection: if the heartbeat is not sent on time (once per minute), the server disconnects the client. Reconnect and resubscribe to the target data stream.
Network-configuration change: after the device IP is changed on the Web page, the current session is disconnected immediately. Log in again using the new IP.
Strategy lock: an enabled alarm strategy/condition cannot be modified or deleted. Disable it first.
Detection limits: the single-detection duration (detection period) can be set from 1 to 30 seconds. The device retains only the latest 50 detection records; older records are overwritten cyclically.
Safety and Maintenance
The default account is admin / 123456. It is recommended to change the password immediately after the first connection under System Configuration → User Management.
“Restore Initialization” resets the IP address, username, and password to their default values and deletes all historical data. Use with caution.
Device logs can be downloaded from System Configuration → Device Logs as system_logs.log. Device Self-Test can be used to check whether the hardware microphones are operating normally.
Binary streams returned by WebSocket (PCM float32, FFT int16, abnormal-noise localization int32, etc.) are parsed in little-endian byte order.
HTTP interfaces uniformly return JSON; ret=200 and msg="SUCCESS" indicate success.
